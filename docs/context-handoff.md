# 上下文交接设计

状态：设计稿，待 Brian 确认后实施。

## 目标与非目标

目标：

- 在 M-Project 内开一个独立版块管理 Session 之间的上下文交接，人和 Agent 看同一份记录。
- 交接内容结构化，待办分「已完成 / 未完成」，下一任 Session 和 Brian 都能直接看清进度。
- 降低交接造成的初始化 token 消耗：交接正文不再在对话里全文输出，也不再整段粘贴进新 Session 的首条消息。
- 交接与需求相互关联，交接不是脱离需求池的游离文本。
- 支持跨 Agent 交接：Claude 写出的交接 Codex 可以领取，未来 Mila 同理。
- 支持同一项目内多条并行工作线，每条各自成链。

非目标：

- 不替代需求池。交接记录的是「一条工作线当前的状态」，需求记录的是「要做什么」。
- 不做跨项目交接。交接与其引用的需求必须同属一个 `project`。
- 不自动开工。领取交接等于接手上下文，不等于获得实现、部署或对外消息授权。
- **不做一对多拆分交接**（Brian 2026-09-21：1:N 会乱，也看不过来）。交接永远一对一。
- **不复制需求内容**。交接只引用需求编号，需求正文和状态去需求那边读。

## 交接与需求的边界

交接模块和需求模块是分开的（Brian 2026-09-21）。交接里要看前任在做的任务，去读那条需求（`#23` 或 `MPROJECT-REQ-…`），不把需求内容抄进交接。

各自管什么：

| | 需求 | 交接 |
| --- | --- | --- |
| 内容 | 要做什么、验收条件、交付证据 | 这一任 Session 的工作状态：做到哪、试过什么、半截的在哪、坑在哪 |
| 生命周期 | 长期，跨多任 Session | 短期，被下一份交接取代 |
| 权威于 | 「这件事做完了没有」 | 「上一任停在哪里」 |

交接只有**一张待办清单**，条目分两种，同列一张表：

- **映射到 REQ 的**：带 `需求:` 指针。需求池里有正式条目。
- **没有 REQ 的**：临时需求，或某一轮就没登记。同样是合法待办，不因为没有编号就被赶出清单。

两边的对齐，靠**现查加比对**，不靠复制：

- 交接里存的是**这一步的进度**（复选框 + 可选 `状态:`）。
- 需求的状态存在需求池里，交接不存。MCP 读取时按 `需求:` 现查，把需求当前状态一并返回。
- 两者不一致时，工具**把差异报出来**，不静默取舍。差异本身就是有用信息：勾了但需求状态没动，说明该去补登记。

因此有一条硬规则：**交接里的复选框永远只表示「这一步做完了」，从不表示「那条需求完成了」**。勾选待办不触发任何需求侧写入；完成需求仍然只能走 `requirements_complete` 并提供完整证据。

### 两个 Skill 的分工

| Skill | 负责 |
| --- | --- |
| `mila-requirements` | 真实需求清单：登记、更新、认领、完成。需求状态只在这里推进。 |
| `update-context` / `resume-context` | 交接上下文：写出和领取一条工作线的当前状态。 |

对齐发生在两个时刻，都不自动写对方：

- **写出交接时**：某条待办已勾选、但它映射的需求状态还停在旧值，Skill 要把这个差异说出来，由 Brian 或当前 Session 决定是否用需求侧工具补推进。
- **领取交接时**：摘要里同时给出待办进度和需求现状，接手方一眼看到哪些对不上。

### 一条待办什么时候该是需求

「靠判断」是需求池要么冗余、要么漏记的真正原因。判据可以从需求合同自身推出来，不需要另立标准：

> **能不能写出不捏造的「用户原文」和「验收来源」？**

- **能** —— 它承载的是 Brian 表达过、或最终需要他验收的意图。那是需求，登记进池子。
- **不能** —— 它是 Agent 自己选的执行路径。那是待办，留在交接里。

这条判据不是行政规定，是硬约束的推论：`requirements_create` 的 `raw_text`（用户原文）和 `requester_type` 都是必填。强制给执行步骤登记需求，等于强制编造用户原文，直接违反 AGENTS.md「用户原文、Agent 理解和讨论分开保存……不能补造」和需求合同「不把 Agent 建议写成用户已确认事实」。**冗余只是难看，捏造来源是污染权威记录。**

另一重理由是粒度：需求是**意图**单位，待办是**执行**单位。一条需求常横跨多任 Session 的几十个步骤。强制一一对应，要么撑爆池子，要么把待办粗化到需求粒度——后者会让交接失去价值，因为「上一任停在哪」恰恰活在那些细节里。

因此**不给 `mila-requirements` 加「待办必须登记」这类规则**。要补的只有上面这条判据，让两个 Skill 对「线划在哪」有一致口径。没有 REQ 的临时待办后来值得正式管理时，由人决定是否登记——登记不自动发生，也不自动授权实现。

引用需求时业务编号和数字工作包号都接受（`resolve` 已支持两者），存储时统一归一化成业务编号，自解释且稳定。

## Token 账本

这是整个设计成立的前提。以下为 2026-09-22 在本地实例上的实测，交接规模取自本项目真实工作量（正文约 2.3 KB）。

估算方法：中文按一字一 token，其余按四字节一 token。这是近似，不是真实分词器的结果，用于比较量级而非精确值。

### 单次交接

| | 字节 | 估算 token |
| --- | --- | --- |
| 旧：写出方把全文写进正文 | 2321 | 701 |
| 旧：下一任粘贴全文进首条消息 | 2321 | 701 |
| **旧流程合计** | | **1402** |
| 新：写出方输出一行 | 103 | 27 |
| 新：下一任取摘要 | 1174 | 310 |
| **新流程合计** | | **337** |

单次降幅 76%。摘要含未完成待办、被引用需求的现查状态、仓库/分支/基线提交。

### 工具面的固定成本

这笔账不算进来就是自欺欺人：8 个交接工具的 schema 会进入会话上下文。

| 加载方式 | 每会话固定成本 |
| --- | --- |
| 完整 schema 全量加载 | 2362 token |
| 仅工具名，用时再取 schema（延迟加载） | 67 token |

### 净收益

| 交接次数/会话 | 全量加载 | 延迟加载 |
| --- | --- | --- |
| 0 | −2362 | −67 |
| 1 | −1297 | **+998** |
| 2 | −232 | +2063 |
| 3 | +833 | +3128 |

**结论取决于加载方式。** 全量加载时盈亏平衡点是 2.2 次交接/会话——对"一个会话交接一次"的典型用法是**负收益**。延迟加载时第一次交接即回本。

Claude Code 对 MCP 工具默认采用延迟加载（工具名先进上下文，调用前再取 schema），因此实际走的是右列。**若某个客户端全量加载 MCP 工具，这个功能在 token 上不划算**，需要另行评估。

### 省下来的从哪来

1. **正文不再承载全文**（确定节省）。
2. **默认分层读取**（主要节省）。若 Skill 写成「接手时总是拉全文」，第 2 项退化，加上工具开销后反而更贵。因此「默认摘要、按需详情」必须写死在 Skill 里，不是建议。

已完成的待办在摘要里压缩成计数，不逐条返回；下一任默认只看未完成项。

交接越长，收益越大：本次测试的交接规模偏中等，长会话产出的交接通常是它的两到三倍。

## OpenProject 建模

### 交接放在哪里

**交接属于项目，就在它引用的需求所在的那个项目里**，作为新的工作包类型 `交接` 存在（与 Task / Bug / Feature 并列）。不是独立项目，也不是游离于项目之外。

三个方案的实际比较：

| 方案 | 判断 |
| --- | --- |
| **独立项目**（建一个 `handoffs` 项目装所有交接） | 否决。交接要与需求建 `relates` 关系，而 `addDependency` 在同一个 `project` 内解析两端，**跨项目关系在现有 API 面上表达不出来**。此外 `AGENTS.md` 一个仓库只记一个项目绑定，会需要第二个；可见性按项目成员判定，要另管一套；看某项目的交接还得离开该项目。 |
| **不属于任何项目** | 不可行。OpenProject 的工作包必须属于某个项目，没有全局工作包。要做就得让交接不再是工作包、自建存储，等于把网页、筛选、历史、附件、`lockVersion`、权限全部重建。代价不成比例。 |
| **同项目新类型** | 采用。同项目关系天然成立，项目绑定不变，权限模型不变，全部既有能力直接复用。 |

### 底层一套，界面分开

数据底层是同一套工作包，**界面上必须分开**（Brian 2026-09-21）：打开项目的工作包列表不该看到交接混在需求里，交接要有自己独立的列表。

这是**两件独立的事**，不能互相代替：

| 层 | 改动 |
| --- | --- |
| **MCP 工具层** | `requirements_*` 查询排除 `交接` 类型。见「对现有行为的改动」。 |
| **OpenProject GUI 层** | 下面这三段。工具层的排除对网页毫无作用。 |

GUI 分离按「优先用 OpenProject 自己的数据模型，其次才动前端」的顺序做：

**一、两个保存视图（纯数据，幂等）**

bootstrap 为每个项目创建两个 `Query` 记录：

| 视图 | 筛选 | 列 |
| --- | --- | --- |
| `需求池` | `type != 交接` | 现有需求列：需求提交人、可见性、负责 Agent、认领 Agent、需求状态 |
| `上下文交接` | `type = 交接` | 交接列：线程、交接状态、待办进度、上一任 Session、更新时间 |

保存视图各自带自己的列集合，这正是需要两个视图而不是两个筛选的原因——两类记录该看的列根本不同。现有 `Setting.work_package_list_default_columns` 是全局的，满足不了。

**二、侧边栏入口**

沿用 `deploy/openproject/mproject_navigation.rb` 里已有的 `Redmine::MenuManager` 模式，在项目菜单下加两个入口，分别指向上面两个视图。

**不替换内置的「工作包」菜单项**。删除再重建它会牵动权限、子项和新建按钮的上下文，风险和收益不成比例。内置入口保留，Brian 走命名入口。

**三、默认落地视图**

点内置「工作包」进去时仍是混合的。能不能把某个保存视图设成项目的默认落地视图，**我不确定 OpenProject 17.8 支持**，需实测。两种结果分别对应：

- 支持：把默认落地指向 `需求池`，收工。
- 不支持：用仓库里已有的前端注入机制兜底——在 `/projects/:id/work_packages` 且 URL 既无 `query_id` 也无 `query_props` 时，往 `query_props` 注入 `type != 交接`。仓库里当时已有 `column-filters.js` 在做同类的 `query_props` 读写，有先例可循。（最终没走这条路：排除交接类型是在服务端的默认查询里做的，见 `mproject_handoff.rb`；那个脚本本身已于 2026-09-22 退役。）

兜底只在「无显式查询」时生效，显式选了别的视图或自己加了筛选就不干预，避免和用户操作打架。

**分离只是呈现，数据仍是一套。** 显式查全部类型时交接照常出现，全局跨项目视图照常可用，`relates` 关系照常跨类型成立。

每个项目各自拥有自己的交接版块。类型和字段是全局定义的，在新项目启用该类型即可，不需要复制一套。

**跨项目总览不会因此丢失**：OpenProject 的全局工作包视图可按类型筛选，用来看「所有项目里等人接的交接」。此条待验证。

### 这套东西有多新

| 新增 | 复用，不重建 |
| --- | --- |
| 1 个工作包类型、8 个自定义字段、1 个保存视图 | OpenProject 整体：网页、筛选、历史、附件、并发、权限 |
| 7 个 MCP 工具 | service 层：项目解析、字段读写、`lockVersion` 冲突、可见性判定、认领原子性、章节读写、关系创建 |
| 待办解析与序列化、线程最新查询 | 项目绑定、需求编号解析 |
| 2 个 Skill | |

是新模块，但长在现有主干上，不是并排另起一套。

### 线程

交接按**线程**串成链：一个线程 = 一条工作线，链上每份交接由上一任写出、下一任领取。新 Session 报出 project 和线程名，就能拿到这条线最新的待接手交接，不需要知道任何编号。

### 交接永远一对一

一份交接由一个 Session 写出，由一个 Session 领取。**不存在一份交接拆给多个 Session 的操作**，也不存在一份交接被多个 Session 同时领取。

Brian 的实际用法（2026-09-21）：一个项目里当前任务基本只有一个 Session，交接就是交给下一个。只有当他发现一条明确无关、无冲突的需求，而当前 Session 正忙于主任务时，才会另开一个独立 Session 处理。

所以多条链是这样产生的，不是拆出来的：

| 来源 | 结果 |
| --- | --- |
| 主任务 Session 交给下一任 | 主线程上一条线性链 |
| Brian 另开独立 Session 处理无关需求 | 该需求自成一个线程，独立成链 |

两条链之间没有父子关系，也没有汇总操作。因此 `上一任交接` 是**单值**，链是线性的。

确需把两条线程合到一起时（少见，且由 Brian 决定），做法是把 A 归档、把 A 剩余待办并进 B 的待办清单——这是一次内容搬移，不是结构操作，不需要专门的工具。

### 线程命名

线程键让并行的链互不干扰，同时要自解释：

- **独立 Session 处理某条需求**：线程键直接用需求编号，如 `MPROJECT-REQ-20260919-001`。自解释，且与需求池对得上。
- **主线**：用工作线标签，如 `m-project/交接功能`。

多数时候一个项目只有一到三个活跃线程。不知道线程名时用 `handoff_list` 看待接手清单。

### 分支是数据，不是前提

**开分支和合并到主线，指令权在 Brian**（2026-09-21）。交接功能因此不能把任何分支写死，也不能假定工作发生在哪条分支上：

- 交接记录的是**实际所在的分支**，不管它叫什么。设计、工具 schema 和 Skill 里都不出现具体分支名作为默认值或判定条件。
- 接手方**不自行切换分支，不自行开分支，不自行合并**。发现本地分支与交接记录的不一致时，报告并等 Brian 的指令，不擅自 `git checkout`。
- 待办里不写「合并到主线」这类动作，除非 Brian 明确交代过。合并时机是他的决定，交接只负责把状态说清楚。

### 接手时怎么核对

分支名相等不是有意义的检查。Brian 可能在两次交接之间下令把分支合进主线并删掉该分支，此时分支名必然对不上，但工作其实一点没丢。

真正要判定的是**基线提交是否仍在当前历史里**：

| 判定 | 含义 | 处理 |
| --- | --- | --- |
| 基线提交是 `HEAD` 祖先 | 工作仍在这条历史上，可能已被合并 | 正常接手 |
| 基线提交存在但不是祖先 | 历史分叉或被 rebase | 停下报告，等 Brian 指令 |
| 基线提交不存在 | 换了仓库或提交已丢失 | 停下报告，不硬接 |

分支名不一致只作为**提示**一并报出，不单独构成阻断。仓库不一致则一律阻断。

### 同分支并行

两个 Session 同处一条分支时（无论那条分支是什么），交接正文必须写明这件事，并要求双方串行操作 git：只 `git add` 自己的文件，绝不 `git checkout -- <dir>` 或 `git stash`——这两个会静默丢掉对方的工作。

### 跨 Agent 交接

Brian 的各个 Agent（Claude、Codex，未来 Mila）**共用同一个用户级 MCP Token**，服务端看到的都是同一个 `brian`。由此：

- 可见性不构成跨 Agent 障碍。私有交接在 Brian 自己的各 Agent 之间同样可读，`公开/私有` 按内容敏感度选，与 Agent 无关。跨**用户**交接才需要公开。
- 跨 Agent 领取、更新、释放**不需要任何权限代码改动**，既有 owner 判定天然放行。
- Agent 名是调用方**自报**的字段，服务端不校验也无法校验。认领冲突真正依赖的是 Session ID 唯一，不是 Agent 名诚实。文档和工具描述都不应暗示这里有强制校验。

接缝划在这里：**MCP 工具面是 Agent 中立的，Skill 是各家自己的壳**。Codex 侧不需要 Claude Skill，只要在它的 `AGENTS.md` 里写一段调用约定；Mila 接入同理。因此工具契约必须自带全部必要信息，不能依赖某一家的 Skill 补话。

随之而来的硬约束：**交接正文里不得出现 Agent 专有内容**——工具名、Skill 名、Session ID 格式假设、某家特有的子 Agent 机制。Codex 读到这些是噪音甚至误导。`注意事项` 章节限定为 Agent 中立事实。

新增 `期望接手 Agent` 字段，默认 `不限`，即任何 Agent 可领。指定具体 Agent 时，`handoff_claim` 要么匹配，要么显式传 `override` 并把原因写进历史。这是协作约定和护栏，不是安全边界。

既有枚举需要补 `Mila`。要统一的是 **Agent 名字本身**，不是选项集合——`不限` 和 `待确认` 描述的是分工意图，对「实际认领者」没有意义：

- `负责 Agent`：`Codex / Claude / Mila / 不限 / 待确认`
- `实际认领 Agent`：`Codex / Claude / Mila`
- `期望接手 Agent`：`Codex / Claude / Mila / 不限`

### 认领接管

`requirements_release` 目前严格要求原 Session ID，owner 和 admin 都不能覆盖（`services/mcp/src/service.ts` 的 `release`，该路径未调用 `assertOwnerOrAdmin`）。后果是**持有认领的 Session 一旦消失，认领永久解不开**，只能到 OpenProject 网页手改自定义字段。

对需求池这是潜伏问题；对交接这是结构性致命——交接的前提就是上一任已经不在，而领取方中途消失同样会卡死整条线程。

因此 `handoff_release` 必须允许 **owner 覆盖释放**：不匹配原 Session 时要求显式接管标记和原因，释放照常执行，接管事件写入变更记录。既有 `requirements_release` 的同一缺口单独评估，不在本设计范围内顺手改。

### 字段

尽量复用既有自定义字段，避免字段膨胀：

| 语义 | 做法 |
| --- | --- |
| 写出交接的 Session | 复用 `来源 Session` |

## 待办模型

正文 `## 待办` 章节存一张 Markdown 任务清单，一行一项，语法固定：

```markdown
- [x] (T1) 重新生成 field-map 并核对键名 · 状态:已完成 · 提交:f8a9227
- [x] (T2) 表头筛选按 schema 出条件 · 需求:MPROJECT-REQ-20260919-001 · 状态:待验证 · 提交:fe8d243
- [ ] (T3) 多用户可见性做重启自启验证 · 需求:MPROJECT-REQ-20260919-001 · 状态:进行中 · 说明:需要真机重启
- [ ] (T4) 把探针 151 置为取消 · 说明:临时事项，无对应需求
```

字段用 `·` 分隔，键固定为 `需求` / `状态` / `提交` / `依赖` / `说明`，缺省即省略。

两个可选键承载 Brian 的两条要求：

- **`需求:`** —— 映射到需求池里的正式条目。有没有 REQ 与勾没勾**完全正交**：未完成的待办照样可以有 REQ（T3 就是），已完成的待办也可以没有 REQ（T1）。四种组合都合法，不存在「没勾说明还没登记」这种推论。
- **`状态:`** —— 这一步在交付管线里的位置，取值与需求生命周期一致：`进行中` / `已实现待提交` / `待验证` / `已完成`。复选框只有勾没勾两态，`状态:` 给出更细的一档，这样「勾了但还没提交」和「勾了且已验收」不会被压成同一个信号。

复选框和 `状态:` 都只描述**这一步**。它们不表示所映射需求的完成度，见「交接与需求的边界」。

### 对齐怎么发生

`需求:` 存的是指针，不是快照。MCP 在读取时按指针现查需求的当前状态，返回值里同时给出三样：

```json
{"id":"T2","done":true,"text":"表头筛选按 schema 出条件","status":"待验证",
 "requirement":"MPROJECT-REQ-20260919-001","requirementState":"进行中","aligned":false}
```

`requirementState` 是现查的，`aligned` 是比对结果。交接里永远不存需求状态，所以不可能对不上——只可能**报出**对不上。`aligned:false` 就是给下一任和 Brian 的信号：这一步交接方认为做到「待验证」了，但需求池里还停在「进行中」，该去补推进。

`aligned` 只在 `需求:` 和 `状态:` **同时存在**时计算。缺其一就没有可比的两端，`aligned` 为 `null`——表示「未比对」，不是「不一致」。这两者必须区分开，否则一条只写了 `需求:` 的进行中待办会被误报成冲突。

完整条目结构：

```json
{"id":"T3","done":false,"text":"重启后自启验证","status":null,"requirement":null,
 "requirementState":null,"aligned":null,"commit":null,"blockedBy":["T2"],"note":"需要真机重启，尚未执行"}
```

选它而不是**子工作包**：一份交接 12 条待办就会产生 12 个工作包，需求池会被执行细节淹没，且每条待办都要走一次创建和权限判定。选它而不是**自定义字段里的 JSON**：Brian 在网页上看不懂也改不了。

任务清单在网页上渲染成复选框，但**在阅读视图里是只读的**（2026-09-21 本地实测，OpenProject 17.8.0 渲染为 `<ul class="op-uc-list_task-list">` 加 `<input type="checkbox" ... disabled>`）。要勾选必须进描述的编辑模式改了再保存，是三步操作而不是一步。

这条实测推翻了本设计早先「Brian 直接勾选即可」的说法，并且是自建模块页面的一个额外理由：页面里复选框的交互由我们控制，可以真正做到点一下就改。原生视图退居为兜底和审计入口。

逐条待办没有独立 journal 历史，只有描述 diff —— 可接受。

勾选只改交接自己的状态，**不触发任何需求侧写入**。完成需求仍然只能走 `requirements_complete` 并提供完整证据。

待办总数和已完成数由服务端在每次写入时从清单重算，不接受调用方自报，避免计数和清单不一致。

### 宽进严出

不管 CKEditor 保存时会不会改写 Markdown，解析都不能指望输入是规范的。人会手打，编辑器会重排，不同版本行为还会变。

- **读取宽容**：接受 `- [x]` / `- [X]` / `* [x]`、缩进、多余空格、被转义的字符、`·` 前后空格有无、`(T1)` 与 `(t1)`。解析不出的行原样保留并标记为无法识别，绝不丢弃——丢一行待办等于丢一件没做的事。
- **写入规范**：MCP 每次写这个章节时，整段按标准语法重新序列化。

这样任何编辑器漂移都会在下一次工具写入时被自动矫正，不需要人工修。设计因此**不依赖** CKEditor 恰好不改写 Markdown；实测的作用降级为「标定宽容度要开到多大」，以及确认复选框确实可交互。

唯一仍然致命的情况是编辑器把复选框语法整段吃掉或转成别的结构（例如变成 HTML 表格）。这一点必须实测确认。

正文章节沿用需求的 `## 标题` 约定，直接复用既有的 `readMarkdownSection` / `writeMarkdownSection`：

```
## 背景        目标、约束、已定决策
## 主线        已做了什么、改了哪些文件、当前实现方向
## 现状        分支与 git 状态、在跑的服务、已执行的验证、已知问题
## 待办        一张清单，条目可选带 需求: 和 状态:
## 注意事项    容易踩的坑、可复用命令、仍然生效的用户指令
## 变更记录    与需求一致
```

## MCP 工具面

命名与既有 `requirements_*` 平行，共用 service 层的解析、权限、`lockVersion` 逻辑。

| 工具 | 用途 | 返回 |
| --- | --- | --- |
| `handoff_save` | 写出或接续一份交接，按 `request_id` 幂等；同线程上一份自动转「已归档」 | 精简回执：编号、线程、待办计数、`lockVersion` |
| `handoff_latest` | **接手第一调用**。按 `project` + `thread` 取最新待接手交接 | 摘要 + 未完成待办 + 被引用需求的**现查状态**与对齐差异 |
| `handoff_get` | 按需拉正文，`sections` 指定章节 | 指定章节 + 全部待办 + 附件元数据 |
| `handoff_claim` | 原子领取，写入接手 Agent/Session/时间 | 精简回执 |
| `handoff_release` | 交还认领；不匹配原 Session 时需显式接管标记和原因 | 精简回执 |
| `handoff_update_todos` | 勾选、新增、改写待办，不动其他章节 | 新的待办计数 |
| `handoff_update_state` | 交接状态流转（归档、作废、交还） | 精简回执 |
| `handoff_list` | 按线程或状态列出交接链，供审计和网页外的回溯 | 摘要数组 + 游标 |

约束：

- 所有工具显式传 `project`，与需求侧一致。
- `handoff_claim` 沿用需求认领语义：已被**其他** Session 领取时返回冲突，不抢占、不重试。同一 Session 重复领取返回 `replayed`。
- `handoff_save` 在同线程存在「待接手」且未被领取的交接时，默认**拒绝**并返回该交接编号，需显式 `supersede: true` 才覆盖。防止两个并行 Session 互相覆盖交接。
- 待办行里 `需求:` 引用到的编号同时建立 OpenProject `relates` 关系，这样从需求页也能看到「哪几次交接碰过它」。
- 交接的任何工具都不写需求状态。勾选待办不触发需求侧写入。
- `handoff_release` 在原 Session 已消失时允许 owner 接管释放，需传接管原因并写入变更记录。没有这条，领取方一旦失联整条线程卡死。
- `handoff_claim` 对 `期望接手 Agent` 的检查是护栏：不匹配时默认拒绝，传 `override` 加原因可放行。Agent 名自报，服务端不校验。
- 没有父子交接，没有批量拆分工具。一份交接一个领取者。

## Skill 改造

### `update-context`（写出方向）

流程改为：

1. 确定线程：沿用本次工作已在用的线程名；没有就按「线程命名」定一个（处理单条需求时直接用需求编号），**不从分支推导**。仓库、分支、`HEAD` SHA 作为属性一并记录，供接手方核对。
2. 取证据：`git status --short`、相关 diff、测试输出。这一步不变。
3. 按结构化字段调 `handoff_save`，待办按上面的语法写。
4. **正文只输出一行**：交接编号、网页链接、`已完成 N / 共 M`。不再输出交接全文。
5. 派发：`ListAgents` 找活跃 peer，**按线程匹配**而不是按分支——同一条分支上可能挂着多条线程，按分支会派错人。`SendMessage` 发的是「接手 `MPROJECT-HO-…`，先调 `handoff_latest`」而不是全文。没有对得上线程的 peer 时，告诉 Brian 开新 Session 并报出编号。
6. 同一条分支上还有别的 Session 在动时，交接正文必须写明，并要求双方串行操作 git。
7. 「绝不开 task chip」的约束保留（Brian 2026-09-19：chip 总是新建 worktree 和新分支，工作必须留在当前主线）。

模板从「一段 Markdown」变成「一组字段」，Skill 携带的是字段契约和待办语法，不再是排版模板。

写正文时遵守 Agent 中立：不写工具名、Skill 名、Session ID 格式假设或某一家特有的机制，因为接手方可能是 Codex 或 Mila。

### 领取方向

已定（Brian 2026-09-21）：**新增 `resume-context` Skill**，触发词 `接手`、`继续`、`接着做`、`领取交接`。`update-context` 只管写出。两个 Skill 描述各自锐利，触发判断不会糊。

这是 Claude 侧的壳。Codex 侧写一段等效的 `AGENTS.md` 约定即可，不需要 Skill；Mila 接入同理。工具契约本身必须自足。

领取流程：

1. `handoff_latest`（project + 线程）拿摘要；不知道线程名时先 `handoff_list` 看待接手清单。
2. 按「接手时怎么核对」判定：仓库必须一致，基线提交必须仍在当前历史里；分支名不一致只作提示报出。不自行切换或开分支。
3. `handoff_claim` 原子领取。
4. 按未完成待办开工；只在摘要不足时才 `handoff_get` 拉指定章节。
5. 干完一段再 `handoff_update_todos` 勾选，而不是攒到最后。
6. 发现原领取方已失联且认领未释放时，用 `handoff_release` 带接管原因接管，不绕开记录直接改字段。

## 交接模块页面

原生工作包页面交互较差，勉强能用（Brian 2026-09-21）。因此交接要有自建的模块页面，交互重新设计；**需求池后续重做一套，复用这套交互逻辑**。

后半句是真正的设计约束：页面不能按「一个交接页」来写，否则复用不会发生。

### 模块跑在 OpenProject 里，不是旁边

第一版把页面做成 `:8081` 上的独立站点，自带 HEAD 和调色板。结果是两个系统而不是一个：页面按 `prefers-color-scheme` 走系统深色，而 OpenProject 按自己的主题走浅色，两边颜色对不上（Brian 2026-09-22）。

现在交接模块是 **OpenProject 里的一个普通页面**：

| 方面 | 做法 |
| --- | --- |
| 外壳 | OpenProject 的 `base` / `global` layout。顶栏、菜单、主题都是原生的，模块只渲染正文 |
| 配色 | 用 OpenProject 的 Primer 变量（`--bgColor-default` 等）。**light/dark 跟随实例，不跟随操作系统**，因此不可能再不一致 |
| 入口 | 全局模块菜单是主入口（跨项目，进去再选项目）；项目侧边栏是同一模块限定到单个项目 |
| 静态资源 | `deploy/openproject/assets/handoff.{css,js}`，经已有的只读挂载由 OpenProject 同源提供 |
| 接口 | 控制器把 `/handoff/api/*` 转发到 MCP，并原样带上浏览器的 session cookie。MCP 的认证逻辑一字未改，同源、无 CORS |
| 路由与控制器 | `deploy/openproject/mproject_handoff.rb`，在初始化器里追加路由并定义控制器 |

MCP 不再自托管页面，只保留 JSON API——不留两套并存。

实施中踩到的四处，都会让功能静默失效或整站 500：

- **匿名类不能调 `menu_item`**：它取 `controller_path`，未命名时为 nil。必须先 `Object.const_set` 再调。
- **每个动作必须声明授权检查**，否则 500。交接的可见性由 MCP 按调用者身份判定，不是项目权限，因此用 `no_authorization_required!`。
- **MCP 的 Host 白名单要包含内部服务名**。代理用 `http://mcp:8081` 调用，Host 头是 `mcp`，不在白名单会被防 DNS 重绑定检查拒掉。
- **菜单项的 url 必须是 Hash，不能是字符串。** OpenProject 通过 `AccessControl.allow_actions(controller:, action:)` 解析菜单项对应的权限；传字符串时它被当作权限**名字**查找，永远找不到，抛 `UnknownPermissionError`。菜单渲染那条路径有 `rescue`（结果是静默隐藏），但 `do_authorize` 没有——任何走到它的请求都变成整页 500。所有内置菜单项用的都是 Hash。

- **控制器需要注册权限**。即使用 Hash，也得有 `OpenProject::AccessControl.map` 注册的权限可供映射。注册要放在 `to_prepare` 里：初始化器阶段 `OpenProject::AccessControl::Mapper` 尚未自动加载。

  `skip_permissions_check: true` 能让菜单那一条绕过检查，但**只治标**：它不阻止别处抛异常，反而让问题看起来消失了。真正的修法是注册权限并用 Hash url。

- **Turbo 导航会丢掉 body 里的 `<script>`**（`<link>` 会保留）。因此模块脚本必须从 layout head 注入（复用 `mproject_navigation.rb` 里已有的品牌 Hook），不能放在控制器渲染的正文里——放正文时脚本从未执行，`turbo:load` 监听器也就无从注册，表现为切走再回来一片空白。脚本自身仍需监听 `turbo:load` / `turbo:render` 并用 `data-mounted` 防重复挂载。

### 必须先解决：两套身份没有桥

系统里存在两个身份空间，目前互不相识：

| 空间 | 身份来源 |
| --- | --- |
| MCP | token → `principals.json` 的 `userId` |
| 网页 | OpenProject session → OpenProject 登录名 |

`canRead` 判定的是 `ownerUserId === principal.userId`，而 `ownerUserId` 由 MCP 写入。网页要套用**同一套**可见性规则，就必须把 OpenProject 登录名映射回 `principals.json` 的 `userId`。这个映射现在不存在。

现有 `/admin/` 页面之所以没碰到：它只管理 `principals.json` 自身，不读需求数据，因此不需要身份。`openProjectAdminAccess` 也只取了 `admin` 位，把用户身份丢掉了。

需要的改动：

- 新增一个同级函数，返回**用户身份**而不只是 admin 布尔；`openProjectAdminAccess` 保持不变，避免动已上线的路径。
- 按 OpenProject 登录名在 `principalStore` 里查对应 principal，查到才用它构造与 MCP 完全相同的 `Principal`，可见性判定因此与 MCP 逐字一致。
- **查不到时拒绝访问**（Brian 2026-09-21），提示该账号去签 MCP Token。可见性判定因此永远与 MCP 逐字一致，不存在第二套规则；代价是新建的 OpenProject 账号要先签 Token 才能用网页。

- **两边命名不一致是常态，必须显式映射。** 实测发现 OpenProject 的管理员登录名是 `admin`，而 `bootstrap-host` 签发的 MCP 身份是 `brian`——按登录名直接找 `userId` 永远找不到，页面对 Brian 自己都打不开。`principals.json` 因此支持可选的 `openProjectLogin`：填了就按它匹配，不填沿用 `userId`（向后兼容）。

  **正式环境升级时必须为 `brian` 补上 `openProjectLogin: "admin"`**，否则交接页面无法访问。这不是本地环境特有的问题。

**没有这座桥，页面上的可见性会和 MCP 的不一致**，同一条私有记录可能网页看得到、Agent 看不到，或者反过来。

不按 OpenProject 登录名直接当 `userId` 用，是因为两套身份的命名一旦分叉（大小写、改名、同名不同人），会错误放行或错误拦截，而这类错误在权限判定里是静默的。

### 为复用而分层

页面按三层写，handoff 只是第一个消费者：

| 层 | 内容 | 复用性 |
| --- | --- | --- |
| 外壳 | 布局、列表/详情、筛选、行内编辑、乐观更新、`lockVersion` 冲突提示、错误呈现 | 与资源无关，需求池直接复用 |
| 适配器 | 某类资源的字段、列、动作、校验、接口路径 | 每类资源一份 |
| 接口 | `RequirementService` 之上的用户级 REST | 两类资源共用同一 service |

先写外壳加交接适配器；后续需求池只需再写一份适配器。若先把交接页面写死，复用不会发生——这是这一节存在的唯一理由。

技术选型跟随现有约束：不引入框架和打包器，保持原生 JS 模块 + 严格 CSP。但不再把 HTML/CSS/JS 挤进单个模板字符串——交接页面比用户管理页面复杂得多，拆成独立文件下发。

### 对原生视图方案的影响

上一节的 GUI 分离方案**大部分仍然需要，但降级**：

- 两个保存视图：保留。纯数据、成本接近零，且是自建页面不可用时的兜底。
- 侧边栏入口：改为指向自建页面。
- 默认落地视图：交接由自建页面消费后，原生列表只需保持「不混入交接」的卫生，优先级下降。

### 范围影响

这一节让工程量大致翻倍：原本是「bootstrap + 7 个 MCP 工具 + 2 个 Skill」，现在增加用户级 REST、身份桥、可复用外壳和交接适配器。

排序上有一条硬约束：**service 层必须保持 UI 无关**，因为 MCP 工具和网页都建在它之上。先 service，再并行 MCP 工具与 REST，最后页面。

## 对现有行为的改动

1. `requirements_list` / `requirements_tree` / `requirements_get` 必须排除 `交接` 类型，否则需求池被交接记录污染。`requirements_list` 目前不传 `type_id` 时返回项目内全部工作包，这是必须改的一处。

## 升级验证

上线正式环境的风险不是"新功能不好使"，而是"把那份真实数据弄坏了却没人发现"。
这两件事需要分开证明，工具也是分开的。

### 数据没坏：快照 + 对账

`deploy/dev/state-snapshot.rb` 只读，本地和生产都能跑。升级前后各取一份，
`deploy/dev/state-diff.py` 负责判定。

**只数条数是数不出数据丢失的。** 某个自定义字段的已填值被清掉一半，工作包一条不少，
按条数验收一路绿灯。所以快照除了条数，还记录**每个字段实际填了值的工作包数**，
以及一份覆盖全部工作包行（id、类型、状态、项目、标题）的摘要。

对账器编码的是上线手册里"全部是追加性改动"那张表：

| 判定 | 内容 |
| --- | --- |
| 预期内 | 新增 `交接` 类型、9 个交接字段、10 处共用字段追加绑定、两个枚举追加 `Mila` |
| 算违约 | 既有类型/字段/项目/用户/状态/查询消失或降级；字段的 id、格式、类型绑定、选项顺序变化；字段已填值减少；工作包或附件内容变化；欢迎页被覆盖 |
| 该做没做 | 交接类型缺失或无工作流（状态变更一律 422）；交接字段绑到了需求类型上（污染需求表单）；共用字段漏绑交接；枚举漏加 `Mila` |

选项检查用的是**子序列**判断而非相等：`Mila` 插在 `Codex Claude` 之后会把 `不限` 的
position 往后推，既有选项的相对顺序不变即为合格。

欢迎页摘要这一条是引导脚本「首次运行判定」失效的探测器——重跑时它一旦被覆盖，
说明脚本把这台机器当成了全新安装，那正是会销毁演示数据和同名查询的那条路径。

### 功能能用：带真实登录态点一遍

`deploy/dev/smoke-handoff.sh` 用自动登录令牌取得会话，逐条请求交接页、项目内交接页、
三个接口，**并且请求原生工作包列表**——菜单项注册错了会让它整页 500，不测就发现不了。
最后跑一次菜单渲染探针，确认菜单不只是注册成功而是真的渲染出来了。

### 演练

`deploy/bin/mproject-rehearse run <生产转储>` 把上面两件事串成一条命令：
恢复转储 → 前快照 → 跑引导并计时 → 校验 `first_run=false` → 后快照 → 对账 → 冒烟。
任一步不过就退出非零并明确说"不要升级生产"。脚本里没有任何通往 `192.168.80.4` 的路径。

引导耗时会被记录，用来估计生产的停机窗口——本地数据量远小于生产，这是唯一能拿到
真实量级的办法。

### 这些工具自己是否可信

一个只会说"通过"的对账器等于没有。`deploy/dev/state-diff-test.py` 自带合成快照，
注入 17 种破坏和 6 种遗漏，要求每一种都被拦下；同时要求忠实的追加性升级被放行。
把对账器里任意一条检查改成恒假，自测立刻报不通过。

### 交接页面（2026-09-21）

`http://<mcp>/handoff/`，与 `/admin/` 同骨架：同源 JSON REST、转发 session cookie 验身份、Origin 校验、严格 CSP、无内联脚本与 CDN。

人在页面上可做：按状态筛选并浏览线程、读全部章节、**直接勾选待办**（原生阅读视图做不到）、整表编辑待办、编辑正文章节、切换交接状态、接管释放卡死的认领、跳转到 OpenProject 原始工作包。

关键取舍：

- **待办计数不由页面计算**，保存后以服务端重算结果为准，避免列表数字与清单本身不一致。

- **网页释放认领一律按接管处理**并记录原因——人不是那个认领 Session，这是唯一诚实的表述。
- 待办上的需求状态是打开页面时现查的，差异以橙色标签呈现，不在页面内代为解决。

#### 与 M Project 的整合

页面不是一个另开的工具，而是系统的一个版块：

- **项目侧边栏入口**「上下文交接」位于「工作包」之后。菜单 URL 是 Proc，OpenProject 会把当前项目传进来（`menu_item.rb` 的 `url(project)`），因此链接自带 `?project=<identifier>`，从哪个项目进就落在哪个项目。

  该项必须带 `skip_permissions_check: true`。渲染项目菜单时 OpenProject 会拿 URL 反查权限（`menu_helper.rb` 的 `node_action_allowed?` → `allowed_based_on_permission_context?`），而外部绝对 URL 映射不到任何 controller，异常被吞掉后返回 false，菜单项被**静默丢弃**。可见性因此交给 `if` 条件，以及页面自身的 session 与 MCP 身份两道检查。

  图标必须是合法的 Octicon 名。`relations` 不是，渲染时抛异常会让**每个项目页面返回 500**，而不是退化成无图标。`arrow-switch` 已验证可用；可用名可直接读其他菜单项的 `@icon`（如 `info`、`history`、`milestone`）。

  **注册不等于显示。** `Redmine::MenuManager.items(:project_menu)` 里能找到该项只说明注册成功。是否显示还要过 `allowed_node?` 与 `visible_node?`，能否显示还要过图标渲染。本项目在这两处各栽了一次：先因缺 `skip_permissions_check` 被静默丢弃，再因非法图标名让整页 500。

  **验证方法**：在 rails runner 里真正渲染一次菜单，而不是只查注册表。

  ```ruby
  controller = WorkPackagesController.new
  controller.request = ActionDispatch::TestRequest.create
  controller.response = ActionDispatch::TestResponse.new
  controller.params = ActionController::Parameters.new(
    controller: "work_packages", action: "index", project_id: project.identifier
  )
  def controller.action_name = "index"
  html = controller.view_context.render_menu(:project_menu, project).to_s
  ```

  渲染成功且 `html.include?("上下文交接")` 为真，才算这个入口可用。权限过滤和图标异常都会在这里暴露。
- **页头是面包屑**「M Project / <项目> / 上下文交接」，可回到 OpenProject 首页、该项目，以及该项目的需求池；切换项目会同步地址栏，页面可直接刷新或分享。
- **交接与需求之间是 OpenProject 原生 `relates` 关系**，由 `handoff_save` 自动建立。因此在需求的原始工作包页面上能看到碰过它的交接，反向亦然。已在本地实例验证（工作包 43 ↔ 42）。
