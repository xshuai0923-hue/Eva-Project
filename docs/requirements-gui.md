## 为什么不直接用原生 API v3

⛔ **非 admin 用户直调 `/api/v3/work_packages` 会看到别人的私有需求。**

`可见性` 只是个自定义字段，OpenProject 不知道它有含义。判定只存在于
`record-service.ts` 的 `canRead`：

```ts
if (principal.role === "admin") return true;
if (ownerUserId === principal.userId) return true;
return visibility === "公开";
```

Brian 2026-09-22 确认：admin 只有他一个，其他用户都不是 admin。所以这条规则是
承重的，**读也必须走 MCP**。

浏览器直调 API v3 本身是成立的（`column-filters.js` 已经这么干，同源带 cookie），
只是不能用来读需求。schema、query form 这类无关可见性的元数据仍可直调。

## 判据一：可见性必须下推到查询，不能内存过滤

`service.ts` 的 `list` 现在是**取全量 → `canRead` 过滤 → 再分页**。

顺序是对的（先过滤后分页，总数和每页条数都准），但它每次调用都把项目里所有工作包
拉进内存。生产现有 113 条无所谓，多用户多项目之后不行。Brian 2026-09-22 要求这一版
就做掉，不留到以后。

⛔ **不能简单地把 `canRead` 写成一条 filter。** API v3 的 filter 是一串 AND，
同一 filter 内部的 values 才是 OR，**跨字段没有 OR**。`公开 OR 自己的` 一条查询
表达不出来——这正是当初退化成内存过滤的根因。

做法是**拆成两条互斥查询再归并**：

```
A: 可见性 = 公开                    + 调用方自己的筛选
B: 可见性 = 私有 AND 需求提交人 = 我  + 调用方自己的筛选
```

- 两边互斥，`total = totalA + totalB` 准确
- 两边都由 OpenProject 服务端按同一个键排序分页
- 取第 N 页时对两个游标做归并，不再有全量加载
- admin 走单条查询，不加可见性条件

`可见性` 与 `需求提交人` 都可筛：bootstrap 对所有自定义字段统一设了
`field.is_filter = true`。

规则仍然只写在 `service.ts` 一处。`record-service.ts` 开头那句注释的告诫依然成立：
`canRead` 有第二份拷贝时，它会静默地朝泄露的方向失败。

## 判据二：项目级可见性目前完全没有

`listProjects` 不收 `principal`，`project()` 也不看调用者。MCP 用服务令牌
（`OPENPROJECT_API_TOKEN`）访问 OpenProject，所以项目的原生 public 与成员机制
对它不生效：**任何已认证身份都能列出全部项目、查任意项目的需求**，只有逐条
`canRead` 兜着。交接页的 `/handoff/api/session` 现在就把全部项目吐给前端。

两条路：

| | 做法 | 代价 |
| --- | --- | --- |
| (a) | 在 `principals.json` 里给每个身份列出可见项目 | 简单，但与 OpenProject 的成员关系各管一套，早晚漂移 |
| (b) | 用 OpenProject 自己的成员 / public 判定，MCP 按身份桥换算后查询并缓存 | 一份权威，照常在 OpenProject 界面管人和项目 |

**定为 (b)**（Brian 2026-09-22）。

### 用哪个查询：已实测

```
GET /api/v3/projects?filters=[{"visible":{"operator":"=","values":["<userId>"]}}]
```

一条查询同时覆盖「成员可见」和「公开可见」，不需要 OR。以服务令牌身份调用，传入别人的 `userId` 即可。

2026-09-22 在本机实例实测（OpenProject 17.8.0），固件：非 admin 用户 `tester`（id 5，**无任何成员关系**），`m-project` 公开、`mila-3` 私有：

| 查询 | 返回 |
| --- | --- |
| `visible = 5` | 只有 `m-project` |
| `visible = 4`（admin） | `m-project` + `mila-3` |
| 服务令牌不加 filter | 两个都有 |
| `principal = 5` | 空 |

⛔ **不要用 `principal`。** 它只看成员关系，**漏掉公开项目**。`user` 这个 filter 不存在。

上述固件留在本机实例里没清，后续验多用户行为直接用。

⚠️ **这一层会改变已上线的 Agent 侧行为**：`requirements_projects` 与
`requirements_list` 会开始拒绝不可见的项目。不是 GUI 独有的变更，升级时要单独说明。

## 判据三：`list` 的筛选与排序要能用

现在写死：

```
filters: type / module / responsibleAgent / state / unclaimed
sortBy:  [["updatedAt", "desc"]]
```

没有全文搜索、不能按任意字段筛、不能换排序、不能分组。照这个做 GUI，交互会更好但
**能力比原生弱**——而 `column-filters.js` 那 316 行干的正是给原生表格补上任意字段
筛选。等于把刚补上的能力拆掉。

放宽的做法是把 filter / sort 表达式透传给 OpenProject，后面那道可见性归并照常生效。
前端不用从零学 OpenProject 的筛选格式：`column-filters.js` 已经会读 query schema、
会构造 filter 表达式，那部分知识搬过来即可，收件人从 URL 的 `query_props` 换成 MCP。

## 按树排、按行分页（2026-09-23 #201，2026-09-25 #258 改为按行数分页）

原来列表按 ID 平铺、每页 50 条，只有父级恰好在同一页时子需求才缩进在它下面。子需求比父级
晚建很多时会落到后面的页：mila-3 的 #148、#192 挂在 #43 下，却在第 2 页，那页只写
「属于 …」。

#201 改成按顶层需求分页：每页 50 条顶层需求，各自连同全部子孙，子需求不占名额。结果一页
可以远超 50 行：mila-3 默认视图（隐藏已完成）80 条、其中顶层 40 条，只有 1 页，翻不了页。
Brian（#258）：「逻辑上应该按绝对数来分页的，子需求也应该被计算在分页里，如遇到跨页了，那
子需求仍然要缩进显示」。

现在：整个匹配先按树排好——顶层按 ID，子需求按 ID 紧跟父级，逐层深入——再每 50 行切一页，
子需求和顶层一样占行。页数 = 「共 N 条」÷ 50 向上取整。一家子被页边界截断时，下一页开头的
子需求照原来的层级缩进，并写「属于 …」。在当前筛选结果里，父级不在结果中的需求算顶层（没有
父级，或父级被筛选、可见性挡在外面），同样写「属于 …」。Agent 用的 `requirements_list` 不变，
仍是平铺分页。

服务端是 `service.ts` 的 `listTree`，页面接口 `/requirements/api/requirements` 走它，每行
带 `depth`（在整棵树里的层级），页面按它缩进父级不在本页的行。

1. 整个匹配只取 ID（`select=total,count,elements/id`）；
2. 用 `parent = <这些 ID>` 取挂在别的匹配项下面的那些的完整记录——`select` 取不到 parent，
   要知道各自挂在谁下面只能读记录本身；
3. 据此排出整棵树，切出本页，本页里还没读过的顶层需求再取完整记录。

所以每次翻页都要读全部子需求的完整记录，外加本页的顶层需求；其余页的顶层需求只走 ID。
ID 按 200 个一组放进筛选条件，查询串不会过长。只按 ID 排序（归并时手上只有 ID），页面本来
就按 ID 升序。匹配超过 2000 条直接报错让缩小范围，不悄悄截断。

在本机实例上实测过（OpenProject 17.8.0）：

- `select` 能取的只有 self、project、status、type、author、assignee、responsible、id、
  subject 等，没有 parent，也没有自定义字段；`elements/_links/parent` 不报错但被忽略。
- `parent`、`ancestor` 筛选都只有 `=`、`!`。`ancestor` 依赖 OpenProject 的层级表，本机较早
  的固件在那张表里没有记录（`_links.ancestors` 为空而 `parent` 有值），`ancestor = 57` 只返回
  74、漏了 58–60，所以只用 `parent`。`parent =` 的值必须是存在的工作包，否则 400。
- ⚠️ **同名筛选条件只保留最后一个，不是「且」**：`id = [57,58]` 再加 `id = [58,59]` 返回
  58、59。`listTree` 加 `id` / `parent` 条件前先去掉同名条件；这些值本来就取自匹配结果，
  结果不变。

测试：`service.test.ts` 的「the pool page pages the tree's rows, children counted」一组；
页面的层级排列在 `requirements.test.mjs`。

## 首页与侧栏（2026-09-23，#183、#184、#185）

首页和需求池分开了。两个侧栏的菜单项相同，依次是 首页、需求池、上下文交接、工作包，
当前页对应的一项高亮。全局侧栏的「首页」是核心自带的那一项，项目侧栏里的是我们加的，
两者都打开 `/`。

`/` 是首页 Dashboard，不再重定向到需求池。控制器和需求池的放在同一个
`mproject_requirements.rb` 里，不用多挂载一个文件；前端在 `assets/dashboard.{js,css}`。

第一版只有按时间段的计数。Brian 看过后说太素、缺当前实际数据，并要求按真正的 Dashboard
该有的样子补齐（2026-09-23）。现在从上到下是：

- **筛选**：项目（全部，或当前用户可见的某一个，数字是所选时间段新建的需求数）和
  日/周/月，可以往前翻；旁边是数据时间和刷新。写在地址里，刷新和分享都保留。
- **新建与完成**：紧跟在筛选下面，因为时间段只管这一块。所选时间段的七个计数；最近 14 天、
  12 周或 12 个月的新建与完成柱状图，图上先用一句话写出所选时间段新建和完成了多少，
  选中的时间段有底色，点柱子切到那一段，悬停看数字，可切成表格；
  所选时间段新建需求的 Agent 热力表。
- **现状**：不受时间段影响的实际数字，七个计数和上面一样；四个清单：等待验收、
  等待确认、停滞 7 天以上（进行中或已实现待提交、7 天没有更新）、待接手的交接，
  每条都能点开，需求打开到需求池里那一条（`?open=`），交接打开到那个项目的交接页；
  状态分布和「未完成的需求 · 按模块」两张条形图；各负责 Agent 的热力表。
- **最近更新**：最近改过的 8 条。

「现状」原先排在最前面。Brian 改了日期，第一屏什么都没变，以为日期过滤没用
（2026-09-23），所以按时间段变化的部分挪到了筛选正下方，项目标签上的数字也改成跟着时间段走。

计数口径（Agent 拟定，Brian 2026-09-23 确认）：

- 「新建与完成」的计数统计创建时间落在所选时间段内的需求，交接不算。日、周、月按读者时区，
  周从周一开始。「现状」不按时间筛。
- 状态按当前状态计。「需求」是 Bug 以外的全部，含 Task。
- 「未认领」是没有 Agent 认领、且没有完成也没有取消的需求，和需求池「实际认领 Agent」列
  的「（未认领）」筛选是同一个意思。所以直接设成「进行中」却没人认领的需求，两边都会计入。
- Agent、模块都取记录上的值，不写死名单；按字段选项排序，没有值的排最后。
- 趋势里的「完成」按交付证据里的「完成时间」归到时间段，重新完成过的取最后一次；
  没有记录完成时间的（比如直接在 OpenProject 改的状态）不计入，图下会说有几条。

数据在服务端算：`GET /requirements/api/dashboard?from=&to=&edges=`，也就是 `service.ts` 的
`dashboard`，外加 `server.ts` 里按项目取的待接手交接。每个可见项目只读一遍全部需求，
走和 `list` 一样的可见性归并，所以别人的私有需求不会进你的数字或清单；现状、时间段、
趋势和清单都从这一遍里切出来。单个项目超过 2000 条会直接报错，而不是悄悄少算。

图表配色取 dataviz 默认色板的前两色（蓝、橙），深浅两套分别对 Primer 的
`#ffffff` 与 `#0d1117` 跑过校验脚本；条形图和热力表只用第一色。

在需求池点「← 全部项目」会清掉记住的项目。否则刷新之后，又会被带回刚离开的那个项目（#184）。
#181 的两页联动不受影响。

测试：`dashboard.test.mjs` 覆盖时间段边界、翻页、地址往返、趋势时间段、坐标刻度、相对时间和
状态顺序；`shell.test.mjs` 覆盖「← 全部项目」清掉记住的项目；`service.test.ts` 的
home dashboard 一组覆盖现状、时间段、趋势（含完成时间取最后一次、无完成时间不计）、
三个清单与最近更新、可见性和交接排除。

变量和 OpenProject 自己的变量取色，所以只重新定义这些变量，读它们的地方都跟着变。我们页面里
选中态、次按钮、头像各用 `--mp-selected-*`、`--mp-button-*`、`--mp-avatar-*`，每处都带着原来
的写法作后备，给没被覆盖的高对比度主题用。

⚠️ 几个坑：

- Primer 按 `[data-color-mode][data-light-theme]` 定义变量，覆盖规则要写在 body 上、多一个
  选择器片段才能不靠 `!important` 赢下来。只覆盖普通的 `light` / `dark` 主题，高对比度主题不动。
- OpenProject 有一批变量在 `:root` 上由别的变量拼出来（`--button--primary-background-color:
  var(--primary-button-color)`、Primer 的 `--text-*-shorthand` 字体简写等）。var() 在声明它
  的元素上就解析掉了，只在 body 上改源变量，这些仍是旧值——原生「创建」按钮因此一直是绿的，
  用简写的组件一直是系统字体。这些要在 body 上重新声明一遍。
- 侧栏当前项原生带一条 5px 的左边框，而且是 `!important`，颜色和底色块同一个半透明色，叠出
  一道更深的竖条。去掉它也得用 `!important`。
- 头像颜色写在元素自己的 style 属性里，改色只能 `!important`。
- 站点图标：OpenProject 只在「没有自定义图标」时输出自己的图标链接，`mproject_navigation.rb`
  让 `apply_custom_favicon?` / `apply_custom_touch_icon?` 答「有」，它就不输出，我们的由 head
  钩子给。两套并存时浏览器用哪一套没有定准。

## 顶栏搜索（2026-09-24，#218）

Brian 要的：只搜我们自己的需求池和上下文交接，搜索框放顶栏，结果分组，支持全文。开工前他定了
四点：按类型分「需求」「上下文交接」两组、每条标项目；搜所有可见项目；全文含评论、不含字段的
历史版本；顶栏下拉预览每组前 5 条，回车或「查看全部」进结果页，每组各自分页、每页 20 条，
命中词高亮并显示命中片段。

- **搜什么**：标题、编号（需求 ID / 交接编号，以及 `#218`、`218` 这样的工作包号）、正文、评论。
  空格分开的多个词要求都命中，但可以分散在不同字段里。各状态都搜，每条标状态。
- **怎么查**：`GET /requirements/api/search?q=&group=&page=&page_size=`，即 `service.ts` 的
  `search`。每个词对四个字段各查一次（`subject`、`description`、`comment`、需求 ID 字段，都用
  `~`），取并集；词与词之间取交集。走全局 `/api/v3/work_packages`，用 `project` 筛选限定到调用者
  可见的全部项目，可见性归并和 `list` 相同。整个匹配只取 id 和类型（`select`），当前页才取整条
  记录，再过一遍 `canRead`。排序：编号命中在前，其次标题命中，再按工作包号倒序。
- **为什么不用 OpenProject 自带的 `search` 过滤器**（17.8.0 实测）：它要求所有词落在同一个字段里，
  「地基 解析器」分别在 #43 的标题和正文，搜不到；它还读全部文本自定义字段，「brian」通过所有者
  字段命中几乎每一条。`select` 也取不了 `updatedAt`，所以没法按更新时间归并排序。
- **页面**：搜索框在顶栏右侧、外观按钮左边（中间留给字标，Brian 2026-09-22）；`/` 聚焦，上下键选、
  回车打开，没选中时回车进结果页。结果页 `/requirements/search?q=`，由 `mproject_requirements.rb`
  里的 `MprojectSearchController` 渲染，不占原生 `/search`。点结果进需求池并打开该需求，或进交接页
  并打开该交接：交接页也支持 `?open=`，按那份交接的状态切到对应标签。
- **输入法**：选字期间（拼音还没确认，或拼音模式下打的英文还没上屏）不出结果，文字确认后再搜；
  选字时的上下键、Esc 也留给输入法。Brian 2026-09-24 在生产上遇到下拉结果要点两次才打开，而
  Chrome 和 WebKit 里用真实鼠标第一次都能打开。最可能的原因是输入法还持有文字时，Safari 把下一次
  点击交给输入法去确认文字，页面收不到。鼠标悬停也不再滚动列表，只有上下键会。
- **上限**：一次最多 100 个字、5 个词；单个词在单个字段上超过 2000 条会直接报错，请加词缩小范围。
- **已知的噪音**：正文模板里的「来源」一节带着「可见性：公开」「提出者」等字样，所以「可见性」这类
  词几乎命中每一条需求；系统写的状态变更、领取记录也是评论，搜「领取」会带出它们。

测试：`service.test.ts` 的「the top bar's search (#218)」一组覆盖跨字段多词、评论命中、只搜这四个
字段、别人的私有记录不出现也不计数、只搜可见项目、两组各自计数、排序、单组翻页、工作包号和命中片段；
`search.test.mjs` 覆盖高亮切分、结果链接、上下键循环、命中说明和短行片段。

## 手机（MPROJECT-REQ-20260928-002，2026-09-28 提出）

Brian 问「能做手机适配吗」。当时在 375px 宽度下：需求池只露出 ID 和需求 ID 两列，标题要左右拖；
点一条后详情排在整张列表下面，看起来点了没反应；顶栏下面空着一截，左边还让出一条给侧栏开关。

三个宽度，各管各的：

| 宽度 | 管什么 |
| --- | --- |
| ≤900px（`shell.js` 的 `COMPACT`） | 需求池表格变卡片，需求池和交接页的详情变成盖住整屏的「页」，筛选的选项从底部升起 |
| ≤640px | 模块页面不再自留左右边距（OpenProject 的 15px 够了），只有第一行给侧栏开关让位 |
| ≤543px | OpenProject 自己的手机布局：顶栏固定在顶上、往下滚时收起 |

- **需求池**：一条需求一张卡片——标题、`#编号 需求 ID`、状态与负责/认领 Agent 与类型；子需求整张卡片
  缩进。表头留着当筛选入口，排成一行可横滑的小标签，常用的在前。取值的筛选从底部升起，下面有遮罩，
  点遮罩只关菜单；要打字的（主题、ID、需求 ID）从顶部落下，不被键盘挡住，键盘上的回车收起它看结果。
- **详情页**：顶上一条「‹ 返回列表」。手机的返回（按钮或从左边缘右滑）也关它，并回到列表原来的位置。
  详情里再点关系里的别的需求，用的是同一条历史记录，返回总是回列表。
- **交接页**同样的详情页和返回；卡片列表左边多出来的 1.6em 缩进去掉了（是 `prose.css` 的 `.mp-list`
  撞了名，宽屏上也有）。
- **首页、搜索页**只调了边距；**备份页、MCP 用户页**的表格在手机上变卡片（备份卡片上把原来窄屏
  藏掉的大小和内容也放回来了，缺附件的备份要看得见）。
- **顶栏**：窄屏上并排两个房子图标（我们为了居中加的 flex 让 OpenProject 本该藏起来的 logo 露了出来），
  现在只剩一个。
- 宽屏（>900px）的布局与行为不变，只有两处宽屏也受益：筛选框的输入法处理（见下）、交接卡片的缩进。

⚠️ 几个只在 iPhone 上出现的坑，都是在 iOS 模拟器的 Safari 里实测出来的，Chrome 和 macOS 的
WebKit 都复现不了：

- **详情页被顶栏压住**。iOS Safari 把 OpenProject 那几层会滚动的盒子（`#main`、`#content-wrapper`、
  `#content`、`#content-body`，`-webkit-overflow-scrolling: touch`）各画成一层，z-index 再高也盖不过
  顶栏。详情页或筛选菜单打开时把这几层改成 `auto`（它们此时本来就锁住不滚），详情页和菜单自己保留
  `touch`。
- **返回把整页重画了一遍，列表位置丢了**。OpenProject 用 Turbo 8，它的 `locationWithActionIsSamePage`
  恒为 false：返回到任何带 Turbo 状态的历史记录都会重新渲染页面。所以打开详情时，先把列表那条记录的
  Turbo 状态换掉、再压一条详情的记录；Turbo 回到没有它状态的记录只会接管、不重画。万一回到这两条
  记录时屏幕上是别的页面（从详情里跟着链接走了再返回），就整页重新载入这一页。见 `createSheetHistory`。
- **按钮文字是蓝的**。iOS Safari 的按钮默认用系统蓝，交接卡片、关系条目、项目卡片没写颜色，
  看着像链接。现在都写了 `color: inherit`。
- **一点输入框页面就放大**。字号小于 16px 的输入框获得焦点时 iOS 会放大页面且不缩回；触屏上输入框、
  下拉框、登录框一律 16px。
- **拼音还没选字就搜了**。主题等筛选框原来每次输入都在 350ms 后搜索，拼音字母被当成关键词，列表变空；
  重画整张表又把输入框换掉，手机键盘就收起。现在选字期间不搜（和顶栏搜索 #218 同一个做法），打字触发
  的搜索只换表格行、计数和翻页，输入框原样留着。这一条宽屏也受益。

测试：`shell.test.mjs` 覆盖窄屏打开详情只占一条历史、返回关闭且不让 Turbo 重画、宽屏不动历史；
浏览器冒烟加了三个手机场景（见 `deploy/dev/README.md`）。
