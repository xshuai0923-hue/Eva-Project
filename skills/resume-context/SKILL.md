# 领取交接

上一任 Session 已经不在了。交接记录了它停在哪里，你的任务是核对环境、领取、接着做。

## 省 token 的关键

**先只取摘要，不取全文。** `handoff_latest` 返回几百字节：线程、仓库/分支/基线提交、待办进度、未完成待办、引用需求的现查状态。绝大多数情况这就够开工了。

只有摘要确实不够时，才用 `handoff_get` 取**指定章节**。一上来就拉全文，这套设计就白做了。

## 步骤

### 1. 找到交接

项目根 `AGENTS.md` 里的 `Eva-Project project` 就是 `project` 参数。

- 知道线程名：`handoff_latest(project, thread)`
- 不知道：`handoff_list(project, state: "待接手")` 看有哪些在等人接，和用户确认接哪条
- 用户直接给了编号：`handoff_get(project, reference)`

`handoff_latest` 返回 null 表示这条线程上没有等待接手的交接——如实说明，不要去翻已归档的。

### 2. 核对本地环境

摘要里有 `repository`、`branch`、`baseCommit`。**分支名相等不是有意义的检查**——用户可能在两次交接之间把分支合进主线并删掉它，此时分支名必然对不上，但工作一点没丢。

真正要判定的是基线提交是否还在当前历史里：

```bash
git merge-base --is-ancestor <baseCommit> HEAD
```

| 判定 | 处理 |
| --- | --- |
| 是 `HEAD` 祖先 | 正常接手，可能已被合并 |
| 提交存在但不是祖先 | 历史分叉或被 rebase，**停下报告**，等用户指令 |
| 提交不存在 | 换了仓库或提交已丢失，**停下报告**，不硬接 |

仓库不一致一律阻断。分支名不一致只作提示报出。

**不自行切换分支、不自行开分支、不自行合并。** 不一致就报告并等指令。

### 3. 领取

`handoff_claim`，传 `project`、`reference`、`agent`、本会话 ID、`label`、`scope`、`claimed_at`。

- 已被**其他** Session 领取时返回冲突：**停下**，不抢占、不重试。除非用户明确说交给你。
- 交接注明了 `期望接手 Agent` 而你不是它：默认拒绝。确需接手时传 `override` 并说明原因，会记入历史。
- 原认领 Session 已经消失、认领解不开时，用 `handoff_release` 带 `takeover: true` 和接管原因接管，**不要绕开记录直接改字段**。

### 4. 开工

按未完成待办做事。待办上的 `需求:` 指针配 `aligned: false` 表示交接方认为这一步做到某个程度了、但需求池里还停在旧状态——这是提示你去补推进需求，不是让你在交接里改。

摘要不够时按需取章节：

- `背景`：目标、约束、已定决策
- `主线`：做了什么、改了哪些文件、当前方向
- `现状`：git 状态、在跑的服务、已执行的验证、已知问题
- `注意事项`：坑、可复用命令、仍然生效的用户指令

### 5. 边做边勾

干完一段就 `handoff_update_todos` 勾选，不要攒到最后。中途断掉时已完成的部分才不会丢。

计数由服务端从清单重算，不用自己报。

**勾选只改交接自己的状态**，不推进任何需求。完成需求要用需求侧工具并提供完整证据：仓库、40 位 commit SHA、路径、验证结果、验收来源。

### 6. 发现交接内容不对

领取后发现某个章节写错了、或者情况已经变了，用 `handoff_update_section` 就地改（`背景` / `主线` / `现状` / `注意事项`，一次一个），在 `note` 里写明为什么改。**不要另写一条交接来纠正旧的**：同一条线上堆出好几条，下一任分不清该看哪一条。

修改章节不推进任何需求，也不改交接状态。

### 7. 交出去

这一任也要结束时，用 `update-context` 写出新的交接，在 `previous` 里指向刚才领取的那份。

## 不做的事

- 不一上来就拉全文。
- 不抢占别的 Session 的认领。
- 不自行切换分支、开分支或合并。
- 不因为领取了交接就认为获得了实现、部署或对外消息的授权——那仍然要用户明确交代。
