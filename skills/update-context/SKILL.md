# 写出交接

交接记录的是**这一任 Session 停在哪里**，让下一任不必重新推导。它存在 Eva-Project 里，人和 Agent 看同一份记录。

## 为什么不再把全文写进对话

旧做法把整份交接写进正文，下一任再整段粘贴进首条消息——同一份文本出现两次，并且永久占据双方的上下文。

现在：写出方只输出一行，下一任调 `handoff_latest` 拿几百字节的摘要，不够时才按章节取。**这条约定是整件事的前提**，正文里再写一遍交接全文就等于白做。

## 前置

项目根 `AGENTS.md` 里的绑定：

```markdown
- Eva-Project project: `eva-project`
```

所有调用显式传这个 `project` 值。没有绑定时先问用户，不从目录名猜。

`handoff_*` 工具不存在时，说明该部署还没上线交接功能——如实报告，不要退回手写全文。

## 步骤

### 1. 确定线程

线程是一条工作线的标识，**不从分支名推导**。同一条分支上可以有多条互不相干的工作线。

- 这一任在处理某条具体需求：线程键直接用需求编号，如 `EVAPROJECT-REQ-20260919-001`
- 主线工作：用稳定标签，如 `eva-project/交接功能`

沿用本次工作已在用的线程名；没有就定一个并说明。

### 2. 取证据

`pwd`、`git status --short`、`git rev-parse HEAD`、`git branch --show-current`、相关 diff、测试输出、关键文件。只写对下一任有用的事实，未知就标为未知，不补造。

### 3. 组织待办

一行一项，语法固定：

```markdown
- [x] (T1) 重新生成 field-map 并核对键名 · 状态:已完成 · 提交:f8a9227
- [ ] (T2) 重启后自启验证 · 需求:EVAPROJECT-REQ-20260919-001 · 状态:进行中 · 依赖:T1 · 说明:需要真机重启
- [ ] (T3) 清理临时探针 · 说明:临时事项，无对应需求
```

键固定为 `需求` / `状态` / `提交` / `依赖` / `说明`，缺省即省略。`状态` 取值 `进行中` / `已实现待提交` / `待验证` / `已完成`。

两条容易写错的：

- **有没有 `需求:` 和勾没勾完全正交。** 未完成的待办照样可以有需求编号，已完成的也可以没有。四种组合都合法。
- **勾选只表示这一步做完了**，不表示那条需求完成了。推进需求状态要用需求侧工具并提供证据。

需求池里没有对应条目的执行步骤同样是合法待办。判断一件事该不该登记成需求，看能不能写出**不捏造的**用户原文和验收来源：能，它是需求；不能，它是待办。

### 4. 写出

调 `handoff_save`：

| 参数 | 内容 |
| --- | --- |
| `project` / `id` / `title` / `thread` | 绑定值、稳定编号（如 `EVAPROJECT-HO-20260921-001`）、标题、线程 |
| `background` | 目标、约束、已定决策 |
| `main_line` | 做了什么、改了哪些文件、当前实现方向 |
| `current_state` | 分支与 git 状态、在跑的服务、已执行的验证、已知问题 |
| `todos` | 上面的清单 |
| `notes` | 容易踩的坑、可复用命令、仍然生效的用户指令 |
| `repository` / `branch` / `base_commit` | 仓库名、当前分支、完整 40 位 HEAD SHA |
| `source_session_id` / `request_id` / `modules` / `visibility` | 本会话 ID、幂等标签、模块、可见性 |

同线程已有未被领取的交接时调用会被拒绝并返回其编号。确认要取代它再传 `supersede: true`，不要习惯性加上。

**正文写作有一条硬约束：Agent 中立。** 不写工具名、Skill 名、Session ID 格式假设或某一家特有的机制——接手方可能是 Codex 或别的 Agent，这些内容对它们是噪音甚至误导。

### 5. 正文格式

正文按普通文本写，网页会渲染三种标记：

- **段首标记变高亮块。** 一段开头放 ⛔（危险 / 红）、⚠️（警告 / 黄）、⭐（要点 / 紫）、💡（提示 / 绿）、ℹ️（注记 / 蓝），整段渲染成对应颜色的块。**只认段首**，句子中间的 ⛔ 还是普通字符；`⛔⛔` 这种重复原样保留。
- `**加粗**` 和 `` `代码` `` 行内渲染。以前不渲染，读的人看到的是星号和反引号。
- 想显式命名类型也可以：`> [!WARNING] 标题` 起一行，紧跟的 `>` 开头各行是块内正文。可用 `NOTE` / `TIP` / `IMPORTANT` / `WARNING` / `CAUTION`。

普通的 `> 引用` 不受影响，引用用户原话照旧写。

**别滥用。** 一段正文通篇都是高亮块，等于没有高亮块。只标真会让接手方踩坑或返工的那几条。

### 6. 写错了怎么改

**用 `handoff_update_section` 改正文，不要重写一条。** 它一次改一个章节（`背景` / `主线` / `现状` / `注意事项`），其余章节和待办一律不动。待办用 `handoff_update_todos`。

**同一个编号重复调 `handoff_save` 改不动它。** 内容一致时按重试返回原记录；内容不一致时直接拒绝，并告诉你哪几个章节不同。

只有工作结论整体变了、且旧交接已经被别人领走时，才写新编号并在 `previous` 里指向旧的。同一条线上堆出好几条交接，接手方分不清该看哪一条。

### 7. 报告

正文**只输出一行**：交接编号、待办进度、网页链接。不要把交接内容再写一遍。

```
已写出 EVAPROJECT-HO-20260921-001（待办 1/3）：<OpenProject 地址>/projects/<project>/handoff
```

发现某条待办已勾选、但它映射的需求状态还停在旧值时，把这个差异说出来，由用户决定是否用需求侧工具补推进。不要自己去改需求。

### 8. 派发

- `ListAgents` 找活跃 peer，**按线程匹配，不是按分支**。多个 Session 常常同处一条分支，按分支会派错人。
- 找到就 `SendMessage` 发一句「接手 `<交接编号>`，先调 `handoff_latest`」，**不发全文**。
- 没有对得上的 peer，就告诉用户开新 Session 并报出编号。
- **绝不投 task chip**（Brian 2026-09-19：chip 总是新建 worktree 和新分支，工作必须留在当前主线）。
- 同一条分支上还有别的 Session 在动时，在 `current_state` 里写明，并要求双方串行操作 git：只 `git add` 自己的文件，绝不 `git checkout -- <dir>` 或 `git stash`。

## 不做的事

- 不写交接全文到对话正文。
- 不推进任何需求状态。
- 不开分支、不合并——那是用户的指令权。
- 不把 Agent 自己选的执行路径登记成需求。
- 不靠重存同一个编号来改交接——存不进去。
